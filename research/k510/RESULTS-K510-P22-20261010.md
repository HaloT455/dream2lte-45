# K510 P22: Exynos8895 Samsung Secure Monitor FMP/SMU bridge

Base: P21 (genuine Linux 5.10.262 AArch64 full `vmlinux` PASS). Donor: pinned Samsung Linux 4.4 V12R5T commit `3ea6f1b4341c0bd9e0e020567fa334da4a1a24c3`.

## Correct original 4.4 ABI, not fabricated SMC semantics

Original `arch/arm64/kernel/exynos-smc.S` uses `dsb sy` + `smc #0` with arguments x0..x3; `drivers/soc/samsung/exynos-smc.c` forwards unmodified arguments and return from `__exynos_smc()`. Original UFS `drivers/scsi/ufs/ufs-exynos.c` configures:
- `SMC_CMD_FMP_SECURITY=0xC2001810`, with arg1=0, arg2 `ID_FMP_UFS_MMC=0`, arg3 `FMP_DESCTYPE_0=0` (without CONFIG_FMP_UFS) **or** `FMP_DESCTYPE_3=3` (with CONFIG_FMP_UFS).
- `SMC_CMD_SMU=0xC2001830`, with args `FMP_SMU_INIT=0, ID_FMP_UFS_MMC=0, 0`.
- Secure log on host reset: `SMC_CMD_LOG=0xC2001860`, args `0,0,2`.
- Disk key loader in `drivers/crypto/fmp/fmp_ufs.c`: `SMC_CMD_FMP_DISKENC=0xC2001820`, `FMP_DISKKEY_SET=1` (NOT ported; strictly required before encrypted storage).

P22 `p22-ufs8895-secure.c` calls **real native** Linux 5.10 `arm_smccc_smc()` and keeps original ARM64 barrier, register ordering, 32-bit x0 result, firmware command IDs and FMP → SMU call order. Raw return code is preserved in `last_firmware_status`; nonzero return fails the bridge with `-EIO` rather than pretending success. P22 has no registered platform driver and no runtime callers.

## Critical PRDT incompatibility discovered

Original Samsung 4.4 `drivers/scsi/ufs/ufshci.h` with `CONFIG_FMP_UFS` expands `struct ufshcd_sg_entry` with extra per-entry `file_iv[4]`, `file_enckey[8]`, `file_twkey[8]`, `disk_iv[4]` and `reserved[4]`, compared with Linux 5.10 `drivers/scsi/ufs/ufshci.h`'s standard 4-entry (16-byte) PRDT descriptor. **The full encrypted Samsung descriptor is 128 bytes per entry, versus native 5.10 16 bytes.** Disabling NSSMU or selecting descriptor 3 without the correct layout or disk-key handoff is not a valid migration.

Original generic Linux 5.10 `ufs-exynos.c` configures `NSSMU` with the comment `make encryption disabled by default`. **That path is NOT equivalent to Exynos8895 secure FMP provisioning.**

## Hard security gates

All P22 secure bridge context gates default false; any attempted secure command returns `-EPERM` until firmware ABI, encrypted PRDT layout, FMP disk key path AND explicit runtime authorization are independently verified. Secure init sequentially calls SECURITY and SMU, never invokes SMU after SECURITY failure. Both return statuses must be zero before marking `secure_storage_ready`.

No SMC is invoked during CI. No UFS hardware probe or flash image is produced. UFS DTB remains `status=disabled`.
